This folder contains code for two comparisons between Maptology and text2term. The first comparison relates to accuracy; for the top-1 or top-5 ontology terms suggested, is the correct term (based on a third-party collection) suggested? The second comparison relates to speed. On average, which method returns results faster?

These benchmarks are performed using input TSV files from the [text2term evaluation repository](https://github.com/rsgoncalves/text2term-evaluation/tree/b999dbb670fa13c9ceb1ba631a7abc7557f3293b), which links to the [UK Biobank to EFO mappings](https://github.com/EBISPOT/EFO-UKB-mappings), [Biomappings](https://github.com/biopragmatics/biomappings), and [OLS mapping downloads](https://www.ebi.ac.uk/ols4/downloads). `code/build_inputs.py` downloads the three source tables from the fixed text2term evaluation commit linked above. It saves them, checks their SHA-256 hashes, and creates the input TSV files under `inputs/`. After running the code, the local `inputs/eval-*.tsv` files contain the selected search strings and correct term IDs. Selection rules, counts, and hashes are recorded in `records/environment-20261031.json` and `records/environment-20261102.json`.

For UKBB-EFO, it keeps `MAPPING_TYPE == "Exact"` and excludes mapping cells containing a comma or `||`, selecting 899 of 1,565 rows. For Biomappings, it keeps EFO targets with `skos:exactMatch`, selecting 796 of 10,431 rows. For OLS-EFO, it skips the 112-line comment block and excludes rows without `object_label`, selecting 9,998 of 35,028 rows. It converts reference IDs to IRIs with Bioregistry. Unresolved references stay in the input with an empty IRI, and repeated rows are kept.

The speed test randomly selects a specified number of distinct strings. Each execution writes the source URLs, row counts, hashes, and package versions to `runs/inputs-<time>/input-verification.json`. The completed download check is recorded in `records`.

The accuracy test uses UKBB-EFO (899 rows), Biomappings (796 rows), and OLS-EFO (9,998 rows). All six methods search the same 29,374 terms from EFO 3.62.0 and return up to five suggestions. A correct term that is outside this search set stays in the test and counts as a miss.

All tests run inside a Docker container, and the graphs are created with R. From this directory on macOS or Linux, run `bash run-benchmarks_Nix.sh`. On Windows, open PowerShell in this directory and run `.\run-benchmarks_Win.ps1`. If desired, you can edit the sample size, repeat count, and output prefixes at the top of the script before running it.

When developing Maptology, we implemented a basic method for searching ontology terms. This method, called `A` in the result files, searches words in each ontology term's name and synonyms as one combined string. `B2` uses the same search technique but puts terms with an exact matching name or synonym first. `E1` starts with `B2` and then searches each name and synonym as a separate string instead of combining them. `E2` starts with `B2` and searches overlapping groups of three characters (3-grams) instead of whole words. `E12` uses both techniques: it searches each name and synonym separately using 3-grams, and it keeps the exact-match priority of `B2`. `T` is text2term 4.5.0, called through its official TF-IDF API. `E12` and text2term share some search concepts, but they use different implementations.

In our preliminary testing, `E12` outperformed the other Maptology variations. Therefore, we used `E12` in the speed comparison against text2term. These benchmarks always use the same strings for both tools. `E12` uses an index loaded before timing. text2term uses its ontology cache and its normal `map_terms` call. Each condition has one warm-up and potentially multiple measured runs, depending on the settings. The timer includes the search call and candidate selection. It excludes imports, input loading, index loading, garbage collection before the call, and result checks. The operating system file cache is not cleared.

The speed test requires AC power. Keep a laptop plugged into its power adapter and awake. The code checks power before and after preparation and every search. Computers without a reported battery are recorded as `no_battery_reported`. Each method and dataset starts in a new process. The process loads its existing index or ontology terms before timing, then runs the searches in order. A new process is not started for every string. The operating system file cache is not cleared. It records a failed call without a time and then stops. Both commands write to new dated folders under `runs/` and leave earlier results unchanged.

These public evaluation sets were used during method development, so the results are not an independent validation. The text2term paper used version 4.1.2, while this benchmark used 4.5.0. The benchmark code is separate from the deployed Maptology app. The published code and TSV tables document the measurements. A full benchmark run on another computer still requires the saved search assets listed in `records/required-assets.tsv`.
